Developer guide

Call POST /route

Send what your agent needs and the rules a route must meet. 402Signal searches and checks candidates, then returns one observed payment option or a typed miss.

Your application keeps its wallet, signs the seller payment, and calls the selected service.

Quick start

Send an unpaid request first

This returns HTTP 402 and a PAYMENT-REQUIRED header with Base, Solana, and Algorand options to authorize $0.003 USDC.

curl -sS -D - https://402signal.com/route \
  -H 'Content-Type: application/json' \
  -d '{"need":"weather data","max_price_usd":0.02}'

Sign one authorization, then retry the same request with PAYMENT-SIGNATURE. 402Signal verifies it before probing and settles it only after finding a valid live eligible route. A normal typed HTTP 503 miss is not settled.

What you can send

Use need to discover and rank services. Use url to check one specific HTTPS endpoint. Either field is enough, and both can be used together.

Discover and rank

{
  "need": "erc20 token balance",
  "prefer_network": "base",
  "max_price_usd": 0.05
}

Check one endpoint

{
  "url": "https://seller.example/x402"
}

Hard constraints fail closed when a required value is unknown. 402Signal does not silently relax them.

What comes back

HTTP 200
A settled routing authorization, a current qualifying target, the exact observed selected_payment, and billing.settled=true.
HTTP 503
Inspect billing.settlement_state before retrying. not_attempted is a free normal miss; settled can mean required transparency failed after settlement; unknown means settlement may have occurred and the authorization must not be reused.
Payment boundary
$0.003 only when a valid live route is found. Normal typed misses are not settled. Seller payment is separate.

PQ Trust

Make routing evidence part of the response

Opt-in proof-carrying routes: add "require_route_binding": true to require a v4 receipt binding the observed seller URL, method, exact request-body hash and complete x402 challenge to a short freshness window. Verify it locally with an independently pinned log key before your wallet signs, and compare the actual current seller challenge. Unknown extensions, redirects, changed terms and unproven request bodies fail closed. This also requires transparency; it does not wait for a Falcon anchor or authorize seller payment. Contract, verifier and limitations.

Set "require_transparency": true when a settled winner must include a durable log leaf and signed checkpoint. A free miss creates no route-decision leaf. If settlement succeeds but the required receipt then cannot be produced, 402Signal returns a fail-closed HTTP 503 whose billing object still truthfully reports settled=true; it does not settle again or call the request free.

A lost or malformed facilitator settlement response is different: HTTP 503 reports settlement_state=unknown and settled=null. Do not reuse that authorization or assume the routing fee was not paid.

The response includes receipt and reveal under pq_trust.transparency. Signed checkpoints are anchored on Algorand MainNet with native Falcon-1024 authorization. The route call does not wait for chain confirmation.

Keep the verification record: securely retain the complete paid /route response, including compared[]. At minimum, later verification requires both pq_trust.transparency.receipt and pq_trust.transparency.reveal. 402Signal does not retain the private reveal and cannot recover it if lost. A modified copy will fail verification against the public log. Because the reveal contains private request and decision evidence, do not put it in public logs.

Scope: Falcon-1024 authorizes the checkpoint transaction. It does not authorize or secure the seller payment.
