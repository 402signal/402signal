An x402 directory finds an API. Who checks it before the agent pays?

September 5, 2026 · Ross, 402Signal

Autonomous buyers need more than discovery and settlement. They need a current decision immediately before signing.

Imagine a research agent needs weather data and can spend no more than two cents. It finds several x402 services in a directory. One listing says the price is one cent. Another claims a faster response. A third supports the agent's preferred payment network.

The agent still does not know which offer it can use now.

The one-cent listing may have changed its price. An endpoint may still be online while returning an incomplete payment request. A service may advertise the right capability but omit the input schema an agent needs to call it safely. The cheapest option may no longer satisfy the buyer's network, latency, or total-cost limits.

A spending cap helps, but it only answers one question. It does not refresh stale metadata, inspect the current payment offer, compare eligible candidates, or explain why nothing qualified.

The missing step sits between discovery and payment

x402 gives software a standard way to encounter a price and authorize payment over HTTP. Directories make paid services discoverable. Facilitators verify and settle payment. Wallets protect keys and apply authorization rules.

The buyer still needs to turn several possible services into one current decision.

402Signal is an independent pre-spend routing check for that step. A buyer sends a capability or specific URL and any hard limits. 402Signal searches supported discovery sources across Base, Solana, and Algorand, calls the strongest candidates, and reads the payment options their endpoints return during that request.

It then applies the buyer's rules to observed options and returns one qualifying route. If no candidate qualifies, it returns a typed reason to stop instead of inventing confidence.

A successful result includes the selected payment option and evidence behind the choice. A miss can distinguish conditions such as no candidates, unusable payment terms, a missing input schema, an expired quote, a timeout, or buyer constraints that were not met.

Why not let the agent do this itself?

A capable agent can be programmed to check an endpoint, parse a payment request, and compare a price. The difficult part is making that behavior consistent across many sellers, discovery sources, payment rails, and failure modes.

Every buyer would otherwise need to maintain its own discovery adapters, network rules, timeouts, payment-term parser, schema checks, ranking logic, and evidence format. That duplicated code becomes part of the spending boundary and has to remain correct as services change.

402Signal packages those checks behind one request. It does not remove the buyer's final authorization. It gives the buyer a current, structured recommendation that can be accepted or rejected under the buyer's own policy.

The agent keeps the wallet

402Signal recommends a route. It does not take custody, hold the buyer's keys, or pay the selected seller.

The buyer keeps signing authority and decides whether to make the seller payment and invoke the service. That boundary matters. A routing service should help an agent decide without becoming another wallet or a new custodian.

The routing authorization is also separate from the seller's price. A buyer authorizes $0.003 USDC for a 402Signal route. 402Signal settles that authorization only when it returns a valid, live, eligible route. A normal typed miss costs $0.

This makes the economic incentive straightforward: finding nothing useful should not be the billable outcome.

Evidence matters once software spends on its own

As autonomous transactions increase, teams will need more than a payment receipt. They will want evidence of what terms were observed and why a route passed the buyer's policy at that moment.

402Signal's PQ Trust layer commits routing evidence to an append-only Merkle log. Signed checkpoints are anchored on Algorand MainNet using a native Falcon-1024 account. If previously published history is changed later, verification should fail.

The scope is deliberately narrow. Falcon-1024 authorizes the checkpoint transaction. It does not make the merchant payment, the seller, or the API response post-quantum secure.

A buyer that wants to verify a particular private decision later must securely retain the verification record returned with the paid route. 402Signal publishes commitments and proofs, not the customer's private routing evidence, and cannot recover that private record if it is lost.

A buyer should be allowed to stop

Autonomous commerce will not become trustworthy by teaching agents to pay every valid 402 response. A payment request is a quote to evaluate, not an instruction to spend.

The useful result is sometimes a route. It is sometimes a clear refusal because the current options do not meet the buyer's rules.

402Signal exists to make that decision current, constrained, and verifiable while leaving control of the money with the agent that owns it.
