Routing flow

What happens during a route check

Start with a capability or a specific URL. Add the limits your agent must follow.

1. Verify authorization
Authorize $0.003 USDC on Base, Solana, or Algorand. 402Signal matches the advertised terms, reserves replay protection, and verifies before route work begins.
2. Find candidates
402Signal searches supported x402 sources, or starts with the URL you supplied.
3. Check endpoints
Candidate endpoints are called before selection. 402Signal reads the x402 payment requirements they return now.
4. Apply your rules
Network, price, latency, invocation requirements, and other limits are applied to the observed options.
5. Settle only a winner
A valid live eligible route settles the routing authorization. A normal typed miss is not settled and its authorization cannot be reused.
6. Caller executes
Your application decides whether to use the route. It keeps the wallet, signs the seller payment, and calls the service.

Billing: $0.003 only when a valid live route is found. Normal typed misses are not settled. On HTTP 503, inspect billing.settlement_state; never reuse an authorization marked unknown. Seller payment is separate.

Scope: a live result means the endpoint returned a usable x402 payment offer during the check. It is not a guarantee about the seller's paid output.

PQ Trust records: if you request transparency evidence, securely retain the complete paid /route response. Private replay outcomes can retain the reveal; they are not a recovery service. Keep your own copy.

Optional route binding: request "require_route_binding": true to bind the observed seller request and payment terms to a signed v4 receipt. Your buyer checks that evidence against the seller's current challenge before signing. Changed terms or expired evidence stop the handoff to payment code. This check does not undo a settled routing fee. Add buyer-side verification.
